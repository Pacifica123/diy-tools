# Markdown Splitter

Статус: `tested` (Linux; Windows — `expected`, не проверялся)  
Зрелость: `M3`  
Версия: `0.3.0`, контракт: `1`  
Флаги: `P, G`  
Основной интерфейс: `cli`

## Что делает

CLI режет большой UTF-8 Markdown-файл на отдельные `.md`-части так, чтобы каждая часть оставалась пригодной для самостоятельного просмотра. В отличие от исходного однофайлового скрипта, граница не ставится посреди произвольной строки после переполнения лимита.

Инструмент:

- не режет fenced code blocks (` ``` ` / `~~~`), Markdown-таблицы, blockquote и отдельные пункты списков посередине;
- распознаёт ATX- и Setext-заголовки;
- если часть продолжается внутри одной секции, повторяет ближайший заголовок в начале новой части;
- если документ начинается текстом до первого заголовка, добавляет синтетический `# <название документа>`;
- пишет части в отдельную папку и не перезаписывает непустую папку;
- создаёт `index.json` с размерами и предупреждениями;
- в конце печатает сводку: сколько частей создано, сколько предупреждений, где результат и отчёт.

Когда использовать: большой `.md` не помещается в лимит загрузки или контекста, и его нужно разложить на куски, каждый из которых читается сам по себе.

## Зачем это исправление

Старый алгоритм проверял лимит перед каждой строкой и при переполнении просто закрывал текущую часть. Поэтому следующая часть могла начинаться с середины абзаца, списка или fenced code block. Заголовок использовался в основном для имени файла, но не как безопасная граница Markdown. В результате отдельные части могли иметь повреждённую разметку.

## Быстрый запуск

Windows:

```powershell
run.bat "D:\docs\large.md" --max-size 1M
```

Linux:

```bash
sh run.sh ./large.md --max-size 1M
```

Напрямую:

```bash
python src/cli.py ./large.md --max-size 500K
python src/cli.py ./large.md --max-size 1M --dry-run
python src/cli.py ./large.md --max-size 1M --json
```

Запускалки не переходят в папку капсулы: относительные пути считаются от папки, в которой вы находитесь. Пути с пробелами и кириллицей берите в кавычки.

Нужен только Python 3.11 или новее, сторонних пакетов нет. Если Python не найден или слишком старый, запускалка и сам CLI сообщают об этом по-русски.

## Вход

Один UTF-8 Markdown-файл (`.md`, `.markdown`, `.mdown`, `.mkd`). Другие расширения допускаются с предупреждением. Переводы строк могут быть `LF` или `CRLF`, BOM в начале допускается; части всегда пишутся с `LF` и без BOM.

Размер задаётся как число байт или суффиксом `K`, `M`, `G`, включая дробное значение: `500K`, `1M`, `1.5M`.

## Выход

По умолчанию рядом с исходником создаётся новая папка:

```text
large_parts/
  001_документ.md
  002_код.md
  003_таблица.md
  index.json
```

Часть называется по своему первому заголовку.

Если `large_parts/` уже существует, выбирается `large_parts_2/`, затем `_3` и т.д. При явном `--output-dir` каталог должен отсутствовать или быть пустым.

`index.json` — аудит-файл нарезки: версия контракта (`contract_version`), имя исходного файла, целевой лимит, список частей с заголовками и фактическими размерами, признак добавленного контекстного заголовка и предупреждения. Все поля описаны в [docs/CONTRACT.md](docs/CONTRACT.md).

После работы CLI печатает сводку:

```text
Готово.
Обработано: 1
Создано: 3
Предупреждений: 0
Ошибок: 0
Результат: large_parts
Отчёт: large_parts/index.json
```

С `--dry-run` ничего не создаётся, сводка показывает план. Коды возврата: `0` — успех, `1` — ошибка обработки, `2` — неверные аргументы или файл не найден.

## Почему `--max-size` мягкий

Главный приоритет — не ломать Markdown. Если один неделимый структурный блок сам больше лимита (например, огромный fenced code block или таблица), инструмент сохраняет его целиком. Такая часть отмечается `oversized=true`, а CLI печатает предупреждение.

Это намеренный компромисс: безопасная структура важнее ложной гарантии «ровно не больше N байт».

## Побочные эффекты и предупреждения

- Удаляет файлы: нет.
- Перезаписывает файлы: нет; непустой явный output-dir блокируется.
- Использует сеть: нет.
- Запускает внешние команды: нет.
- Читает потенциально приватный текст: да (`P`). В сеть ничего не отправляется. Текст документа в `index.json` и в вывод не попадает, но имя исходного файла и тексты заголовков — попадают (в `index.json`, в имена частей и в список частей на экране).
- Генерирует новые `.md` и `index.json`: да (`G`). Границы частей выбираются эвристикой (best-effort): перед тем как отдавать части дальше, просмотрите `index.json` — предупреждения и части с `contextHeadingAdded` — и при сомнении сами части. Исходный файл не изменяется.
- Незакрытый fenced code block считается ошибкой: инструмент не создаёт заведомо сломанные части.

## Границы применимости

Это не полный CommonMark-парсер. Инструмент защищает основные многострочные конструкции, из-за которых практическая нарезка чаще всего ломается: code fences, таблицы, blockquote, списки, HTML-блоки с явным закрытием, абзацы и заголовки.

Reference-style links и footnotes не копируются автоматически между частями. Если определение ссылки находится далеко от места использования, отдельный chunk может потерять кликабельность ссылки, хотя сама Markdown-структура останется валидной.

## Контракт

Внешний контракт (аргументы, коды возврата, формат входа, имена частей, поля `index.json`, что идёт в stdout/stderr и что контрактом не является) — в [docs/CONTRACT.md](docs/CONTRACT.md). Версия контракта: `1`; она же записана в каждом `index.json` как `contract_version`. Несовместимое изменение = новая версия контракта и запись в CHANGELOG.

## Проверка

```bash
python scripts/smoke_test.py
```

Тест запускается из любой папки, пишет только во временную папку, не требует сети и сторонних пакетов. Он запускает настоящий CLI на примерах из `examples/input/` и побайтно сравнивает части и `index.json` с эталоном в `examples/output_expected/<имя примера>/`:

| Пример | `--max-size` | Что проверяет |
|---|---|---|
| `sample.md` | 200 | текст до первого заголовка, код с `#` внутри, таблица, список |
| `Большой документ с пробелами.md` | 420 | имя с пробелами и кириллицей; ATX и Setext; ` ``` ` и `~~~`; таблица, цитата, списки, HTML, код с отступом; секции больше лимита с повтором заголовка |
| `oversized_block.md` | 300 | блок кода и таблица больше лимита — путь с предупреждением |
| `frontmatter.md` | 300 | YAML front matter остаётся в начале первой части |
| `без заголовков.md` | 260 | документ без заголовков: синтетический заголовок в каждой части |

Кроме сравнения с эталоном проверяется, что:

- склейка частей без добавленных заголовков даёт все непустые строки исходника в том же порядке;
- каждая часть начинается с заголовка и сама разбирается без ошибок (блоки не разорваны);
- часть больше лимита есть только вместе с предупреждением в `index.json`, размеры в `index.json` совпадают с файлами;
- тот же документ с `CRLF` и BOM даёт побайтно тот же результат;
- `--dry-run` ничего не пишет, а его план совпадает с настоящим результатом;
- непустая выходная папка и повторный запуск ничего не перезаписывают;
- незакрытый fence, пустой файл, не-UTF-8 и отсутствующий файл дают понятное сообщение и нужный код возврата, ничего не создавая;
- `run.sh` работает из чужой текущей папки с относительным путём.

Чего проверка не делает: Windows и `run.bat` не запускались (`run.bat` проверен только по тексту); примеры маленькие — скорость и память на файлах в сотни мегабайт не измерялись (файл читается в память целиком); редкие конструкции CommonMark вне списка из раздела «Границы применимости» не покрыты.

Проверить руками на примере:

```bash
python src/cli.py examples/input/sample.md --max-size 200 --dry-run
```

## Как изменить под себя

Вся логика находится в `src/cli.py`:

- `parse_blocks()` — разбор на защищённые Markdown-блоки;
- `split_blocks()` — мягкий лимит и контекстные заголовки;
- `sanitize_filename()` — переносимые имена частей;
- `write_chunks()` — запись `.md` и `index.json`.
